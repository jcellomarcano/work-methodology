# Feature: skill-evals

**Objective.** One command tells the owner, per skill, whether it works or needs review and why: it runs fixed cases with and without the skill on Claude Code's own eval tool, scores them with three scorers in cascade, and refuses a run that cheated.
**Branch.** `feat/skill-evals` from `main@c9e2770`; merge into `main` and push are the owner's word. Delivery `ask-on-risk`; forecast above 400 authored lines, so the chain choice is asked before the second task's commit if it holds. Runners: `cd 08-benchmark && METODO_MEMORY=off python3 -m unittest discover tests`; `cd 03-tools && METODO_MEMORY=off python3 -m unittest discover tests`; `python3 03-tools/lib/docs_lint.py 03-tools/config/docs-caps.json --tokens 03-tools/config/token-caps.json`. Risk: item 5 (it launches paid model runs and a tool that publishes a report unless told not to) and item 6 for the parts only a live run proves.

- **S2 Case format, owned by the kit.** A case is a folder `08-benchmark/evals/<skill>/<case>/` with `case.json`, `prompt.md`, and optionally `setup/`, `testdata/` and `validators/`. `case.json` carries: `schema_version`, `skill`, `tier` (`smoke`, `core` or `deep`), `expected_skills`, `setup.files`, `forbidden_paths`, `ablation_exempt_paths`, `validators`, `expectations`, and the run limits (`max_turns`, `timeout_seconds`, `allowed_tools`, `runs`). JSON, because the kit ships no YAML parser. A `validate` command rejects an unknown key, a missing required key, a path that leaves the case folder, a `setup.files` entry that stages anything under `testdata/`, and a case with no scorer at all; it prints one line per problem and exits 1.
- **S3 Staging.** `setup.files` are copied into the run's working directory before the agent starts. `testdata/` is the answer key for the validators: it is never staged and is always a forbidden path.
- **S4 On the native tool.** The runner builds, per skill, a throwaway Claude Code plugin holding only that skill, writes each case in the native layout (`prompt.md`, `case.yaml`, `graders/*.md`) and runs `claude plugin eval` on it, always with `--no-publish`, a cost ceiling and a results folder inside the kit's out folder. Tiers become native tags. With and without the plugin is the ablation of that one skill; `ablation_exempt_paths` are what stays in both arms. What the native tool cannot do is done by the kit around it and said in the report.
- **S5 Three scorers in cascade.** (1) Trigger: every skill in `expected_skills` was invoked. (2) Script validators: each script exits 0 against the files the run left, with `testdata/` at hand; deterministic. (3) LLM judge: an independent model checks the final answer against each `expectations` sentence. A later scorer's result counts only when the earlier ones passed: a case that failed scorer 1 is "not triggered, quality not judged", never "bad quality". Where the native tool spends on the judge anyway, the report says so.
- **S6 Anti-cheat.** A run that read or wrote a `forbidden_paths` entry is `cheated`: it scores nothing and is counted apart. The check is deterministic.
- **S7 Verdict per skill.** The report gives each skill one of `works`, `review` or `not measured`, with the reason in plain words: it does not trigger when it should (look at the description), it triggers and changes nothing (dead weight: cut or shrink), it triggers and the result is worse than without it, its output fails a validator, or the judge rejects it. Beside the verdict: cases run, arms, the with and without scores and their difference, the skill's size in tokens, and the spend. A verdict from fewer than three runs per arm is labelled a signal.
- **S8 Only what changed runs again.** A result is stored under a hash of the skill's files, the case's files and the runner's version; a case whose hash has a stored result is skipped and reported as cached, unless `--no-cache`.
- **S9 Rules.** Python 3 standard library only. Tests never start a real `claude`: the binary is a stub named by an environment variable, as the A/B runner does. No test and no default command spends money; a real run needs an explicit flag and prints its cost ceiling first. Artifacts in English. No line cap raised. Every command, flag and path named in a document exists (the path test of `tests/test_doc_commands.py`).
- **S10 Seed and proof.** At least two skills get one `smoke` case each, and one real run of one case is made as proof, under a ceiling of USD 1, its result kept in `odd/research/`. (Assumption of the parent: which skills and that ceiling.)
- **S11 Not in this feature.** The rules index with a rationale per rule and a detector (the goal's rule-to-linter item); Bazel or Starlark as the engine; publishing a package to any marketplace; installing a type checker on the owner's machine; evals under pi, Antigravity or Codex (the native tool is Claude Code only); running the whole seed suite at three runs per arm (the owner's spend decision).
- **S12 A BUILD per skill (owner, L5).** Each skill has one declaration beside its sources, `02-skills/<skill>/BUILD.json`, with the verifiable pieces the owner named: `agent_skill` (the skill's markdown, its references and its scripts, plus what it needs from the kit, packed into one zip with a manifest so it can be placed in a marketplace as an add-on), `validate_skill_test` (the front matter is well formed), `py_type_test` (strict type check of the skill's Python), `py_test` (its unit tests) and `eval_suite` (every case is valid against the schema and every file it names exists). One command builds or tests one skill or all of them, runs again only the targets whose inputs changed (the hash of S8), and prints one line per target: PASS, FAIL, or SKIP with its reason; a SKIP is never counted as a pass. The package of `agent_skill` is the plugin the runner of S4 evaluates, so what is measured is what ships. The BUILD file itself is neither installed into a target repo nor packed. JSON and a small executor in the kit (assumption of the parent: the owner asked for the declaration and its checks, "como blaze", not for Bazel). Open: the type checker. The owner named pytype; none of pytype, mypy and pyright is installed on this machine (Measured, 2026-11-23), so the target reports SKIP with that reason until one is.

- **S13 A kit plugin for the skills that need the server (owner, L13).** Beside the package per skill, which stays the unit that is verified and evaluated, one more target builds a single Claude Code plugin of the kit: every skill, plus the kit's MCP server and what it needs to run from inside the plugin, with the skills' tool names written as the plugin exposes them. It is a byte-identical zip with a manifest, built by the same command, and it holds no personal file, no test and no BUILD file. Proof: one real run in which a skill that needs the server, loaded from that plugin alone, calls one of its tools and gets an answer. Publishing it to a marketplace stays out (S11). Assumption of the parent: skills and server only; the kit's hooks and role agents inside the plugin are a later decision.

- **S14 The arm without the skill keeps the skill's tools (owner, L26).** When a run carries the kit's MCP server (`--kit-mcp` or `--kit-plugin`), the arm without the skill runs on the same plugin with only the measured skill's folder removed: the server, its tools and their names stay, so the difference between the arms is the skill alone. Without a server the native with-and-without ablation stays as it is. Every command line still carries `--no-publish` and a cost ceiling, and nothing is spent without `--real`. The report says how the arm without the skill was built. Assumption (parent): done as two native invocations with `--ablation none`, because the native ablation removes the whole plugin, server included.

- **S15 The `change-card` case asks for what only the skill does (owner, L26).** The seed case of `change-card` stops asking for a bare validation, which one tool call answers, and asks for the work the skill's own text governs: draft a missing field without inventing evidence or a tag the author did not give, leave "Why", "What it risks" and the Ticket to the author, and say what goes to the owner. The prompt reads as a user would type it and does not name the skill. A script validator checks the file the run leaves; the judge checks the answer.

- **S16 Benchmarks (owner, L27).** "y haz los benchmarks". Assumption (parent's reading): real runs at three runs per arm of the skills that have cases, under the written ceiling of USD 0.25 per skill, kept under `odd/research/`.

- **S17 A case for each of the other 15 skills (owner, L29).** Each skill that has no case gets one `smoke` case in the kit's format. The case asks for the work the skill's own text governs, not for what one tool call answers; its prompt reads as an owner would type it and names no skill, tool or validator; a deterministic validator with its answer key in `testdata/` checks the files the run leaves, fails a careless run and does not fail a faithful one for a reason the skill does not state; a test file runs that validator on a faithful output and on one output per broken rule; two or three expectations ask the judge for substance, not for wording. Where the format cannot exercise a skill (it needs role agents, a git history, an interview with the owner or a real pull request), the case measures the part that can be measured and the page says what is not; where nothing can be, the skill gets no case and the reason is written. Then every skill with a case is run for real at five runs per arm under USD 0.25 per skill. Assumptions (parent): model and judge `haiku`, as in every run so far; a writer may make at most two real runs per skill, at one run per arm under USD 0.10 each, to see its case trigger.
