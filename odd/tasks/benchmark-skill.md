# Feature: benchmark-skill

**Objective.** A benchmark skill and tool that can land on `main`: the model is told to use it whenever a harness, kit or review setup has to be measured, it runs the same in a vanilla Claude Code session and inside the kit, and it computes the metrics the October 2026 landscape research says are worth measuring.
**Branch.** `feat/benchmark-skill` from `origin/main` @ `a22062b` (GitHub clone). Delivery `ask-on-risk`: forecast above 400 authored lines; the PR strategy is asked before any push. Runners: `cd 03-tools && METODO_MEMORY=off python3 -m unittest discover tests`; `cd 08-benchmark && python3 -m unittest discover tests`. Risk: item 3 is not touched (no existing contract changes); the A/B runner launches `claude -p` processes with a tool allowlist (item 2) → independent verifier at the end.

## Specs

- **S1 Request (owner, verbatim).** "necesito que trabajes en una skill y una tool que peudan ir a main para poder hacer le benchamrking y que al llm le diga que la use para hacer el becnhmark, tambien lo peuda hacer en vanilla, e investiga cuales son los puntos fuertes que realmente vale la pena medir y compara este trabajo con todo lo existen de este kind en internet que permita esclaracer dinde realmente se esta agregando valor". Scope chosen by the owner: "Medición + A/B (Recomendado)" — observational per-session mode plus the A/B runner with k repetitions, pass^k, paired CIs and two-family blind judges; the seeded-defect task suite is a later PR.
- **S2 Research artifact.** The landscape report (`odd/research/benchmark-landscape/report.md`) is committed in English, scrubbed of absolute local paths and client names, with its sources and labels intact.
- **S3 Portable skill.** One self-contained skill folder (`02-skills/harness-benchmark/`): `SKILL.md` plus the scripts it calls inside the same folder, Python 3 stdlib only, no `metodo` MCP server, no kit hooks, no `__TOOLS_DEFAULT__` dependency. Copying the folder into `~/.claude/skills/` (or a repo's `.claude/skills/`) is the whole vanilla install. Inside the kit it is shipped by the installer like the other skills. Its scripts have one source of truth: `08-benchmark/lib` (the skill's copies are generated by a sync script and a test fails when they drift).
- **S4 Trigger.** The `description` tells the model to use the skill whenever it is asked to measure, benchmark or compare a harness, kit, methodology, review setup, model/effort choice or "with vs without" a tool, and never to compare setups from a single run or from impressions.
- **S5 Observational mode.** `bench session [--project <repo>] [--since <date>]` reads Claude Code transcripts (and an OTel export when given) and reports, per session and per group, with a label on every number: activation (kit strong markers, skills, MCP servers used), tokens by type, cost (with its source named), peak context and occupancy against a window table, compactions, delegation shape (subagent token share, subagents by type), model × effort mix, human steering (turns, including mid-turn messages), wall-clock. No prompt or reply text leaves the script; deterministic output.
- **S6 A/B mode.** `bench ab` runs the same task prompt under named arms (at least: `vanilla`, `kit-neutral`, `kit-invoked`, `native` = a prompt that invokes a native review/skill), `k` repetitions per arm (default 3), randomized order, same model and effort, clean working tree per run, and records each run's session id, cost, turns, findings, status. Arm validity: a non-vanilla arm whose transcript does not match its evidence pattern is `invalid-arm`, never scored.
- **S7 Statistics.** `bench report` computes, per arm and per task: pass@1, pass^k and verdict-flip rate when a deterministic verifier is given; cost per solved task; paired task-level bootstrap 95% CI of the difference vs `vanilla` and vs `native` (fixed seed, so it reproduces); and states "not shown" when the CI crosses zero.
- **S8 Judges.** Deterministic checks first. LLM judging only for finding validity: findings normalized to one schema (kit fingerprints such as epistemic tags and `path:line@sha` stripped), two judges from different model families when configured (one family is allowed but reported as a limitation), every pairwise comparison in both orders, an `Unknown` option, and agreement between judges reported.
- **S9 Labels and honesty.** Every reported number carries Measured / Tested / Inferred / Assumed / Unknown and a status (`ok`, `failed`, `not-run`, `invalid-arm`); n is printed next to every comparison; a single-run comparison is printed as a signal, never as a conclusion.
- **S10 Kit integration.** The kit ships the skill through the existing installer list and documents it; the MCP and init integrations of the earlier `bench-module` branch are out of scope for this PR.

### Contract shared by T2 and T3

- Sources of truth in `08-benchmark/lib/`: `transcript_metrics.py` (existing), `bench_session.py` (T2), `bench_ab.py` (T3), `bench_cli.py` (T2). `08-benchmark/bin/sync-skill.sh` (T2) copies them into `02-skills/harness-benchmark/` as top-level files (`bench_cli.py` becomes `bench.py`), because the installer copies only top-level files of a skill folder; a test fails when a copy drifts.
- CLI: `bench.py session [--root DIR] [--project PATH|SUBSTR] [--since YYYY-MM-DD] [--out DIR]`; `bench.py ab --config ab.json [--out DIR] [--dry-run]`; `bench.py judge --run DIR`; `bench.py report --run DIR [--out DIR]`. `bench_cli.main(argv)` dispatches `session` to `bench_session.main(argv)` and `ab`/`judge`/`report` to `bench_ab.main_ab/main_judge/main_report(argv)`.
- Transcripts: `${CLAUDE_PROJECTS_DIR:-~/.claude/projects}`; a repo's dir is its `realpath` with every non-alphanumeric character turned into "-" (helper `transcript_metrics.transcript_dir(path)`).
- Runs: each A/B run executes in a fresh `git worktree add --detach` of the repo at the pinned sha, outside the repo; an arm's `overlay` lists untracked paths copied from the repo into that worktree (the kit's `.claude/`, `.mcp.json`), so a vanilla arm sees no kit file at all. `CLAUDE_BIN` overrides the binary (tests use a stub).
- The skill is not a kit marker: `harness-benchmark` stays out of `KIT_SKILLS`, so measuring a vanilla session that used it does not flag the kit.
- Router: arms are not routed by design (one model and effort for every arm, from the config); judge models are explicit in the config.
